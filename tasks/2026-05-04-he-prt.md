# Hyper-Expansion (HE) PRT Implementation

**Date:** 2026-05-04
**Goal:** Unlock the Hyper-Expansion PRT for race selection and wire its engine-side coefficients (×2 growth multiplier, ×0.5 population cap), starting fleet (1 armed scout + 3 Mini Colony Ships), and component-catalogue restrictions (Mini-Colony Ship, Meta Morph, Settler's Delight, Flux Capacitor are HE-only). Population cap factors for JOAT (×1.2) and AR (×0) are wired in the same step since the dispatch lives in one place.
**Relevant PRDs:** [22 — Race Design](docs/prd/22-race-design.md) §"PRT-Driven Engine Coefficients", §"Primary Racial Traits", §"Schema Changes" (catalogue restrictions); [14 — Population & Habitability](docs/prd/14-population.md)

---

## Background

Phase A (`2026-04-26-race-design-phase-a.md`) shipped JOAT-only race selection. The JOAT-effects follow-up (`2026-05-03-joat-effects.md`) added JOAT starting tech, fleet, and built-in scanner. HE is the second PRT to land.

The HE PRT effects from the PRD that this task implements:

1. **×2 growth multiplier** — applied inside the PRD 14 `population_growth` step. The race's stored `max_growth_rate` is unscaled; HE doubles it at calculation time.
2. **×0.5 population cap factor** — multiplied into `max_population`. JOAT (×1.2) and AR (×0) factors are wired through the same dispatch even though only HE and JOAT are selectable today.
3. **Starting fleet** — 1 armed scout + 3 Mini Colony Ships (each with Settler's Delight engine).
4. **Catalogue restrictions** — `prt_required` on Mini-Colony Ship hull, Meta Morph hull, Settler's Delight engine, Flux Capacitor. `build_design` rejects any owner whose race PRT is excluded. Symmetrical `prt_forbidden`, `lrt_required`, `lrt_forbidden` fields are added on the same schema change so future PRT/LRT work doesn't churn the catalogue type again.

Out of scope for this task:

- **Cannot build stargates** — stargates aren't implemented as a buildable starbase component yet. When the Stargates PRD lands, that PRD reads `race.prt == HE` and forbids construction. This task adds no enforcement.
- **Flux Capacitor +20% beam damage** — combat is owned by PRDs 80–82. The component already has `electrical.ability: 20` in the data file; combat resolution will read this when wired. This task only restricts who can build it.
- **HE predefined preset (Silicanoid)** — Silicanoid uses HE plus the LRTs IFE / UR / BET / OBRM, all gated. Land it with the LRT phase.
- **Meta Morph design seeding at game start** — Meta Morph requires `construction: 10`, far above starting tech. It only becomes buildable mid-game. The task adds the catalogue tag; build-time validation already enforces the tech gate.

## Step 2 — Population cap factor and growth multiplier

The PRD specifies (§"PRT-Driven Engine Coefficients") that HE has `growth_multiplier = 2.0` and `population_cap_factor = 0.5`; JOAT has `population_cap_factor = 1.2`; AR has `population_cap_factor = 0` and is excluded from cap calculations entirely. This step wires all three through one dispatch even though AR remains gated by the validator.

Edit [population.py](backend/openstars/engine/resolve_steps/population.py).

- [ ] Add a module-level table `_POPULATION_CAP_FACTOR: dict[PRT, float] = {PRT.HYPER_EXPANSION: 0.5, PRT.JACK_OF_ALL_TRADES: 1.2, PRT.ALTERNATE_REALITY: 0.0}` and a helper `def population_cap_factor(prt: PRT) -> float` returning the table value or `1.0` for any PRT not listed.
- [ ] Add a module-level table `_GROWTH_MULTIPLIER: dict[PRT, float] = {PRT.HYPER_EXPANSION: 2.0}` and a helper `def growth_multiplier(prt: PRT) -> float` returning the table value or `1.0`.
- [ ] Change `max_population(hab, race_hab)` signature to `max_population(hab, race_hab, *, cap_factor: float = 1.0)`. Multiply the final integer by `cap_factor` and floor: `return floor(BASE_MAX_POPULATION * max(hv, 5) / 100 * cap_factor)`. Calling without `cap_factor` preserves the existing behaviour for tests that have not been migrated yet.
- [ ] Change `population_growth(...)` signature to take an optional `growth_multiplier: float = 1.0` keyword argument and apply it inside the `growth_rate` calculation: `growth_rate = (hv / 100) * (max_growth_rate / 100) * growth_multiplier`.
- [ ] In `grow_population(ctx)`, look up the planet owner's race PRT once per planet and pass `cap_factor=population_cap_factor(race.prt)` into `max_population` and `growth_multiplier=growth_multiplier(race.prt)` into `population_growth`. Pass the same `cap_factor` into the `population_death` overcrowding-deaths call (overcrowding_deaths takes `max_pop` directly so it stays consistent).
- [ ] In [fog.py](backend/openstars/engine/fog.py) (line ~227 and the analogous detailed-scan branch around line 280), pass `cap_factor=population_cap_factor(owner_race.prt)` into the `max_population` call. Import `population_cap_factor` from `openstars.engine.resolve_steps.population`.
- [ ] Unit tests in [test_population.py](backend/tests/engine/test_population.py):
  - `population_cap_factor(PRT.HYPER_EXPANSION) == 0.5`; for JOAT == 1.2; for AR == 0.0; for SS == 1.0.
  - `growth_multiplier(PRT.HYPER_EXPANSION) == 2.0`; for JOAT == 1.0.
  - `max_population(...JOAT-equivalent hab/race...) ` with `cap_factor=0.5` returns half the previous value (rounded).
  - `population_growth(...)` with a HE-equivalent setup (cap_factor=0.5, growth_multiplier=2.0) returns roughly 2× the increment of the equivalent JOAT setup at low population (the cap difference is irrelevant below 25% capacity).
  - At a HE planet near max population, the cap halving causes growth to slow earlier compared to JOAT under the same `max_growth_rate`.
- [ ] Unit tests in [test_fog.py](backend/tests/engine/test_fog.py) (or analogous): `derive_player_state` for an owned planet of a HE player reports `max_population` halved compared to the same planet owned by a JOAT player, all else equal.

## Step 4 — Catalogue PRT/LRT restriction fields

Add the four optional restriction lists from PRD 22 §"Schema Changes" to `ComponentCatalogueEntry`. The fields are loaded from YAML (default empty) and read by `build_design` to gate construction.

Edit [component_catalogue.py](backend/openstars/engine/component_catalogue.py).

- [ ] Add four optional fields to `ComponentCatalogueEntry`, each defaulting to an empty `list[str]`:
  - `prt_required: list[str] = Field(default_factory=list)` — entry is only buildable if the owner's `race.prt` is in this list (or the list is empty, meaning no PRT restriction).
  - `prt_forbidden: list[str] = Field(default_factory=list)` — entry is forbidden if the owner's `race.prt` is in this list.
  - `lrt_required: list[str] = Field(default_factory=list)` — entry is only buildable if every LRT in this list is present in `race.lrts`.
  - `lrt_forbidden: list[str] = Field(default_factory=list)` — entry is forbidden if any LRT in this list is in `race.lrts`.
  - Use `list[str]` (not the `PRT`/`LRT` enums) to keep the catalogue YAML decoupled from the race-models import; validation maps the strings to the enums at lookup time.
- [ ] Tag the four HE-only catalogue entries by editing the YAML:
  - [hulls.yaml](backend/openstars/data/hulls.yaml) — add `prt_required: [HE]` to the `mini_colony_ship` and `meta_morph` entries.
  - [components/engines.yaml](backend/openstars/data/components/engines.yaml) — add `prt_required: [HE]` to the `settlers_delight` entry.
  - [components/electrical.yaml](backend/openstars/data/components/electrical.yaml) — add `prt_required: [HE]` to the `flux_capacitor` entry.
- [ ] Unit test in [test_component_catalogue.py](backend/tests/engine/test_component_catalogue.py) (existing file, add cases):
  - Loading the catalogue produces `mini_colony_ship.prt_required == ["HE"]`, `meta_morph.prt_required == ["HE"]`, `settlers_delight.prt_required == ["HE"]`, `flux_capacitor.prt_required == ["HE"]`.
  - An entry without restriction fields parses with all four lists empty.
  - A catalogue entry with `prt_required: [WRONG]` (string the loader doesn't recognise) still parses — the loader is a passthrough; validation against the PRT enum happens at design-build time.

## Step 5 — Enforce restrictions in `build_design`

Edit [designs.py](backend/openstars/engine/designs.py).

- [ ] Define a new `DesignValidationError` code: `RACE_RESTRICTED`.
- [ ] Extend `build_design`'s signature with an optional `race: Race | None = None` keyword argument. Import `Race` and `PRT` / `LRT` from `openstars.engine.race.models`.
- [ ] Add a private helper `def _check_race_restrictions(entry: ComponentCatalogueEntry, race: Race | None) -> None`:
  - If `race is None`, return — legacy callers that don't pass a race (e.g. some unit tests) keep their existing behaviour. Production call sites should pass the race.
  - If `entry.prt_required` is non-empty and `race.prt.value not in entry.prt_required`, raise `RACE_RESTRICTED` with detail "{entry.name} is restricted to {entry.prt_required}".
  - If `race.prt.value in entry.prt_forbidden`, raise `RACE_RESTRICTED` with detail "{entry.name} is forbidden for PRT {race.prt.value}".
  - If `entry.lrt_required` is non-empty and any required id is missing from `{lrt.value for lrt in race.lrts}`, raise `RACE_RESTRICTED`.
  - If any `lrt.value in entry.lrt_forbidden` for `lrt in race.lrts`, raise `RACE_RESTRICTED`.
- [ ] Call `_check_race_restrictions` once for the hull entry (before the existing `_first_unmet_tech_requirement` check) and once per component assignment after its tech check. Match the existing ordering convention: hull is validated before components.
- [ ] Find every production call site of `build_design` (`grep -rn "build_design(" backend/`) and pass the owner's race through:
  - [turn_zero.py](backend/openstars/engine/resolve_steps/turn_zero.py) `_build_starting_fleet` — pass `race=ctx.race_by_username[username]`.
  - [production.py](backend/openstars/engine/resolve_steps/production.py) (or wherever build orders consume `build_design`) — same pattern, look up `ctx.race_by_username[planet.owner]`.
  - The designer router under `backend/openstars/server/routes/` (likely `designs.py` or `designer.py`) — look up the caller's `Player.race`.
  - Any other caller surfaced by grep.
- [ ] In whichever server route handles design submission, translate `DesignValidationError(code="RACE_RESTRICTED", ...)` into HTTP 400 with the same `code`/`detail` shape as the existing tech-locked / unknown-component errors.
- [ ] Unit tests in [test_designs.py](backend/tests/engine/test_designs.py):
  - Building a Mini Colony Ship design for a JOAT race raises `RACE_RESTRICTED` with the expected detail.
  - Building a Mini Colony Ship design for an HE race succeeds.
  - Building a Scout design (no restriction) succeeds for both JOAT and HE.
  - Building a design that includes a `flux_capacitor` component for a JOAT race raises `RACE_RESTRICTED` even if the hull is unrestricted (covers the per-component check, not just the hull).
  - Calling `build_design` without `race=` (legacy path) does not raise on a restricted hull — backwards-compat smoke test.
